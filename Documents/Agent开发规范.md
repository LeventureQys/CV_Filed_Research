## Agent 开发规范

仅供 Agent 阅读。

### 适用规模

- **大规模 Version**：需求点 ≥ 5，或存在明显可并行子任务、代码依赖复杂 —— 拆 Stage/SubStage，SubAgent 并行开发。
- **小规模 Version**：需求点少、依赖简单 —— MainAgent 独立完成。

无论规模，都遵守：**问题清单驱动、零猜测、零上下文交付、新功能强制单元测试 + 启动测试**。

---

### 1. 核心原则

#### 1.1 Version-Stage 拆分

- **Version**：一组大需求，语义化版本号（如 `v1.2.0`）。
- **Stage**：按代码依赖串行执行的开发阶段。
- **SubStage**：Stage 内可并行的最小工作单元，交给 SubAgent。
- SubAgent 之间**不直接沟通**，所有接口契约由 MainAgent 提前定义。
- Stage 完成后跑增量系统测试；Version 完成后跑全量回归。
- SubStage 失败最多重试 3 次，仍失败则暂停并重规划。

#### 1.2 问题清单驱动（核心）

任何开发前，MainAgent 列出所有不确定点，写入 `问题清单.md`，按置信度分区：

- **置顶区**（阻塞开发）：置信度 < 90% 或涉及重大技术路线分歧的问题。等用户答复。
- **自决区**（不阻塞）：≥ 90% 置信且无路线分歧的问题。MainAgent 自主决策，但完整记录方案与自决理由。

**问题清单的迭代机制（重要）：**

1. **v1**：Version 开发正式启动前，MainAgent 梳理需求生成 `问题清单.md`，作为**独立回复直接发给用户**，正文只放清单，不夹带其他工作。
2. **等答复**：用户答复前不做任何开发或拆分。
3. **v2、v3 ...**：用户答复后若引出新问题，**追加到同一份清单末尾**，标记 `## v2 追问`、`## v3 追问` ...，同样以独立回复发送并等待答复。
4. **清空为止**：**置顶区所有问题被答复关闭后，才能进入下一步**（Stage 拆分或开发）。
5. **开发中新问题**：Stage 内部出现不确定点，按同样规则追加到对应 Stage 的 `问题清单.md`。

#### 1.3 零上下文交付

任何开发 / 验收文档，都要让一个全新 Agent 在没有对话历史的情况下能独立理解、执行、判断。

---

### 2. 角色分工

| 角色 | 职责 |
|------|------|
| **MainAgent** | 拆分 Version/Stage/SubStage；维护问题清单；编写设计与验收文档；分派 SubAgent；协调测试与验收；处理异常与重试。 |
| **SubAgent** | 按任务书开发，不扩边界；遇不确定立即停并报告 MainAgent；完成后自测并报告；不与其他 SubAgent 沟通。 |
| **验收 Agent** | 只依据验收文档 + 设计文档 + 完成报告 + 仓库当前状态验收；不依赖对话历史；每项给出通过/失败/阻塞并附证据；文档不清则要求补充。 |

---

### 3. 开发流程

#### 3.1 Version 规划

1. 确认需求并分配语义化版本号。
2. 创建 `问题清单.md`（v1），梳理所有不确定点，按 1.2 分区。
3. **以独立回复把 v1 清单发给用户，等答复**。
4. 用户答复后若引出新问题，追加 `v2 追问`，继续独立回复等待，反复直到置顶区清空。
5. 清单清空后，拆小需求点并按依赖排列 Stage 顺序。
6. 起草 Version 级验收框架，标注硬件 / 外部 / 人工依赖。

#### 3.2 Stage 规划

每个 Stage 开始前：

1. 创建 Stage 级 `问题清单.md`，按 1.2 分区并按 v1/v2 迭代直到置顶区清空。
2. 拆分 SubStage，写清跨 SubStage 契约（数据、接口、路径、字段、生命周期、错误处理）。
3. 编写 **Stage 设计文档**（满足 6.1 零上下文可开发）。
4. 编写 **Stage 验收文档**（满足 6.3 零上下文可验收）。
5. MainAgent 自检通过后再分发 SubStage。

#### 3.3 Stage 执行

1. **分发**：任务书含输入、输出、验收标准、禁止事项、相关路径、跨 SubStage 契约。
2. **SubAgent 开发**：遇不确定立即停并报告；MainAgent 按 1.2 处理后同步文档并恢复。
3. **自测**：按任务书执行测试 / 构建 / 检查，报告命令与结果。
4. **汇总集成**：MainAgent 处理冲突、接口偏差、文档同步。
5. **Stage 测试**：
   - 全量单元测试（新功能强制含新增逻辑测试）。
   - 增量系统测试。
   - **启动测试**（新功能强制，见第 4 节）。
   - 失败定位到 SubStage 并重试，最多 3 次。
6. **Stage 验收**：按验收文档逐项验收，记录通过/失败/阻塞与证据。文档不清则先补文档。
7. **交付物**：设计文档、验收文档、完成报告（含启动测试证据）、最终问题清单（含自决记录）。

#### 3.4 Version 收尾

- 全量系统测试。
- 按 Version 验收文档全量验收。
- 检查所有问题清单无未关闭项、所有文档互相一致。
- 产出 Version 总结报告：Stage 汇总、测试结果、验收结论、版本号、变更日志、清单归档。
- 打 tag（如 `v2.1.0`）。

---

### 4. 测试与验收

**新功能 / 较大更新**（满足任一即算）：

- 新增功能模块、对话框、数据流、协议实现、Modbus 寄存器路径。
- 新增文件 ≥ 3 个 或 影响文件 ≥ 5 个。
- 涉及信号槽新连接、跨线程通信、OpenGL/QChart/QML 渲染改动。
- 触及"Critical Recurring Bugs"任一模块。

**强制**：单元测试 + 启动测试，缺一不可。不允许仅凭编译通过就报告完成。

- **单元测试**：新增 / 修改核心逻辑写 gtest / QtTest，覆盖正常路径 + 至少一个边界 / 异常，实际执行并通过。
- **启动测试**：实际启动 `TactileSense.exe`，走一遍新功能核心路径，验证无崩溃、无异常日志、UI 无异常。证据（截图说明、日志片段、操作记录）写入完成报告。

**小规模修改**（≤ 2 文件、纯 bug fix、无新增数据流）可豁免启动测试，但既有测试须跑通。

| 类型 | 触发 | 范围 | 输出 |
|------|------|------|------|
| 单元测试（全量） | 每 Stage 结束；新功能强制 | 全部用例 | 完成报告测试章节 |
| 系统测试（增量） | 每 Stage 结束 | 本 Stage 影响面 | 完成报告测试章节 |
| **启动测试** | **新功能 / 较大更新完成后** | **本机启动 + 核心路径** | **截图 / 日志 / 操作记录** |
| Stage 验收 | Stage 测试通过后 | Stage 验收项 | Stage 验收记录 |
| 系统测试（全量） | Version 所有 Stage 结束 | 整个系统 | Version 测试记录 |
| Version 验收 | 全量测试后 | Version 完整交付 | Version 验收结论 |

**启动测试通过标准**：

- 应用无崩溃启动，主窗口正常显示。
- 新功能入口可触发，进入后无立即崩溃。
- 核心操作路径至少完整走一遍无异常。
- `qDebug/qWarning/qCritical` 无与改动相关报错；spdlog 无 ERROR。
- 无法本机启动（缺硬件、需真实设备）：完成报告写明阻塞原因，并追加到 `问题清单.md` 置顶区。

---

### 5. 异常处理

- **SubStage 失败**：MainAgent 通知重试，最多 3 次；重试前可要求分析原因。
- **3 次失败**：暂停 Stage，重新拆分 SubStage 或重写 Stage 方案。
- **开发中不确定**：追加问题清单，按 1.2 处理，关闭后同步文档。
- **验收失败**：定位 SubStage 修复；验收标准不清则先修文档再验收。
- **不允许**：
  - SubAgent 擅改任务边界。
  - 验收者用对话历史代替验收文档。
  - 无法执行的验收项默认通过。
  - 跳过启动测试就报告新功能完成。

---

### 6. 文档标准

| 工件 | 时机 | 说明 |
|------|------|------|
| Version 问题清单 | Version 规划前 | 按 6.2 分区，含 v1/v2 迭代记录 |
| Stage 问题清单 | Stage 规划前 | 同上，Stage 特有 |
| Stage 设计文档 | Stage 开发前 | 满足 6.1 |
| Stage 验收文档 | Stage 开发前，不晚于分发 SubStage | 满足 6.3 |
| Stage 完成报告 | Stage 测试和验收通过后 | 改动清单、测试结果、启动测试证据、验收结果、问题清单闭环 |
| Version 验收文档 | Version 规划或首 Stage 前 | 全量验收范围、跨 Stage 集成、硬件依赖、通过标准 |
| Version 总结报告 | Version 全量验收后 | Stage 汇总、全量测试、验收结论、版本号、变更日志、清单归档 |

#### 6.1 零上下文可开发

Stage 设计文档 / SubStage 任务书要包含：

1. **背景与目标**（1-3 句，不用"如之前讨论的"等引用）。
2. **当前代码状态**（相对路径 + 必要行号）。
3. **完整接口契约**（数据结构、枚举、常量、字段名、生命周期、错误处理）。
4. **输入输出**（来源、去向、格式）。
5. **验收标准**（可测试、可观察）。
6. **禁止事项**（不该改的模块 / 文件）。
7. **依赖前置**（依赖产物的位置、格式、可用条件）。

自检：新 Agent 读完能否直接开工？是否有依赖对话历史的表述？接口是否可直接写代码？

#### 6.2 问题清单标准

**每条问题包含：**

1. **问题描述**：定位到具体文件 / 模块 / 行号。
2. **建议方案 / 说明**：基于代码与上下文给出推荐答案。
   - 优先鲁棒性和可测试性。
   - 解决实际问题，不加无用抽象。
   - 不以"简单快速""开发成本低"作为理由（开发由 Agent 执行，工期不是约束）。
3. **风险预警**：无法由 Agent 规避的风险标注"需用户决策"。
4. **备选方案**：多条合理路径或推荐方案风险高时，给 1-2 个备选并对比。
5. **置信度**：百分比或高 / 中 / 低。
6. **分区归属**：
   - ≥ 90% 且无路线分歧 → **自决区**，写自决理由。
   - < 90% 或有路线分歧 → **置顶区**，阻塞开发。

**推荐结构：**

```markdown
# 问题清单 - vX.Y.Z / StageN

## v1（初次梳理，YYYY-MM-DD）

### 置顶区（待用户确认，阻塞开发）

#### Q1. 问题标题
- 问题描述：...
- 建议方案：...
- 备选方案：...
- 风险预警：...
- 置信度：70%
- 归入置顶原因：例如"两种方案对后续扩展性差异显著，需用户拍板"。

### 自决区（≥ 90% 置信，已自决，不阻塞开发）

#### Q2. 问题标题
- 问题描述：...
- 自决方案：...
- 自决理由：例如"Python reference `src/device_center/protocol.py:123` 已有明确实现"。
- 风险预警：...
- 置信度：95%

## v2 追问（用户答复 v1 后新引出的问题，YYYY-MM-DD）

### 置顶区
...
### 自决区
...
```

**迭代机制：**

- 每次生成或追加清单后，**以独立回复发送给用户**，正文只放清单，不夹带其他工作。
- 用户答复前不做任何开发或拆分。
- 用户答复后若引出新问题，追加 `## v2 追问`、`## v3 追问`，继续独立回复等待。
- **置顶区所有问题被答复关闭后**，方可进入下一步。

**自检：**

- 每个问题都有建议方案和置信度吗？
- 置顶区是否只包含真正需要用户决策的问题？
- 自决区的自决理由是否充分（避免用虚高置信度绕过用户）？
- 用户仅凭置顶区能否作"同意 / 否决 / 选备选"的判断？

**不允许：**

- 无建议的裸问题。
- 多个独立问题塞一条。
- 建议里省略风险。
- 用"赶工""简单"作为核心理由。
- 不写入清单直接开发（100% 有把握也要落自决区）。
- 明显 ≥ 90% 且无分歧的问题塞置顶区打扰用户；反之，有分歧或低置信度问题塞自决区跳过用户决策。

#### 6.3 零上下文可验收

验收文档要包含：

1. **验收范围**（覆盖 / 不覆盖）。
2. **验收环境**（系统、构建配置、测试数据、硬件、外部服务、账号）。
3. **前置条件**（仓库、配置、数据、设备初始状态）。
4. **验收项列表**（唯一编号、目的、操作步骤、期望结果、通过 / 失败标准）。
5. **证据要求**（命令输出、文件路径、日志片段、截图说明、人工记录）。
6. **失败与阻塞处理**（何时记录、重试、追加问题清单、退回开发）。
7. **回归范围**（历史功能哪些回归、哪些冒烟、哪些不覆盖）。
8. **交付物检查**（必须存在的文档、报告、配置、样例数据）。

**验收项格式：**

```markdown
### A1. 验收项标题
- 目的：...
- 前置条件：...
- 操作步骤：...
- 期望结果：...
- 通过标准：...
- 失败标准：...
- 证据要求：...
```

**不允许：**

- "按之前讨论"、"看起来正常"等主观表述。
- 只写命令不写期望输出与失败处理。
- 无法执行的硬件 / 人工验收项默认通过。
- 开发完成后才补验收标准。

---

### 7. 强制门禁

以下任一违反，都不能标记 Stage / Version 完成：

- **置顶区未清空**：问题清单里还有待用户确认的问题。
- **验收标准不清**：验收文档缺项或存在主观表述。
- **新功能未跑启动测试**：或未在完成报告中提供启动测试证据 / 豁免说明。

---

### 8. 目录结构

```text
Document/Update/vX.Y.Z - 版本名称/
├── 需求文档.md
├── 问题清单.md
├── 验收文档.md              # Version 级验收
├── 总结报告.md              # Version 完成后
├── Stage1/
│   ├── 问题清单.md
│   ├── 设计文档.md
│   ├── 验收文档.md
│   └── 完成报告.md
├── Stage2/ ...
└── StageN/ ...
```

Stage 很小时，验收文档可作为设计文档的独立章节；但存在多 SubStage、硬件依赖、外部依赖或人工验收时，独立成文。
