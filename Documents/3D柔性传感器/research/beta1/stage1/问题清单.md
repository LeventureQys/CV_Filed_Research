#### Q2. “处理白噪音”的目标是检测/估计噪声，还是输出降噪后的传感器帧？
- 问题描述：需求要求框架“先是分析器，然后是处理器，二者独立开来”，并“暂时只处理白噪音”。这里可能有两种目标：一是识别每通道噪声统计并生成噪声模型；二是实际对每帧 ADC 数据做抑制输出。
- 建议方案：本阶段定义为“白噪声分析 + 白噪声抑制原型框架”：Analyzer 从背景噪声数据学习每通道基线、方差、采样率和置信门限；Processor 对输入帧按通道执行基线扣除、白噪声门限抑制、非负裁剪，并输出处理帧与诊断指标。
- 备选方案：只做 Analyzer，不定义 Processor 输出；风险是无法验证“处理框架”在压力工况下是否保留有效信号。
- 风险预警：如果用户期望的是频域 Wiener 类完整降噪，当前传感器数据采样率偏低且非音频信号，直接套用音频 NS 结构可能不合适。
- 置信度：75%
- 归入置顶原因：目标定义会决定算法复杂度、测试指标和后续是否需要频域处理。

回复：不，这里还是要让你做好一个完整的框架流程，不要只做一边，先有了完整的框架然后我们再来调整。这里是需要你根据白噪音的情况得到一个结果的，我们根据你的结果，再来反馈如何进行下一步的工作。

#### Q3. 是否确认不利用空间邻接关系，只做逐通道统计处理？
- 问题描述：需求提出“假设这个块的位次之间实际上是没有物理上的连接关系的，只从统计学上去考虑噪声与否”。数据中手套与织物垫为 12×8，64×32 膜片文件头显示 `行数,64`、`列数,64` 但压力目录名为 64x32，且背景文件 `数据点数,0`，存在设备元数据不一致。
- 建议方案：算法设计阶段完全按一维通道序列处理，不做邻域滤波、形态学、连通域或空间平滑；rows/cols 仅作为显示/元数据，不参与噪声判断。
- 备选方案：保留可选空间后处理接口但默认关闭；风险是违背本阶段“只从统计学考虑”的假设，扩大范围。
- 风险预警：逐通道处理能避免错误空间假设，但无法利用真实触点在空间上连续这一事实，可能对孤立异常点更保守。
- 置信度：85%
- 归入置顶原因：空间关系是否彻底禁用会影响框架接口和测试解释。

回复：目前暂时不要考虑空间邻接关系，暂时只考虑统计学上的降噪算法。当然了，实测过程中你也可以尝试考虑，我们来做一下横向比对。

#### Q4. 白噪声处理的验收指标应优先看哪一类效果？
- 问题描述：现有数据集包含背景噪声、500g/1kg/1.5kg 等压力工况，但需求没有给出量化验收指标。手套背景噪声约 20Hz 采样，织物垫背景噪声约 10Hz，64×32 背景噪声约 2Hz 且大量为 0，不同设备难以用同一固定阈值验收。
- 建议方案：使用离线指标验收：背景段总值均值下降、背景段非零/误触发通道数下降、压力段峰值保持率、压力段总值保持率、处理延迟为单帧 O(N)。每套设备分别统计，不强行统一绝对阈值。
- 备选方案：用固定 ADC 阈值作为全设备验收；风险是对手套/织物垫/64×32 三类设备不公平。
- 风险预警：没有人工标注触点真值时，只能用背景段与压力段的弱监督指标评估，无法证明每个触点位置都完全正确。
- 置信度：70%
- 归入置顶原因：验收指标决定后续测试报告和算法参数调优方向。

回复：按照建议方案来。

#### Q6. 噪声类型扩展方式如何预留？
- 问题描述：需求要求白噪声、棕色噪声、粉色噪声均可处理，但当前暂时只处理白噪声。
- 自决方案：框架文档中定义 `NoiseKind` 或等价概念：`White` 可用，`Pink`/`Brown` 仅保留分析器与处理器接口、参数占位和“不启用”行为，不设计具体算法细节。
- 自决理由：这满足扩展性要求，同时避免在研究数据不足时过度设计粉色/棕色噪声处理。
- 风险预警：后续启用粉色/棕色噪声时，需要补充更高采样率或更长时间序列数据来估计频谱斜率。
- 置信度：92%

#### Q7. 是否直接照搬 WebRTC NoiseSuppressor 的 FFT/Wiener 频域路径？
- 问题描述：`NoiseSuppressor_Teaching_Document.md` 描述的是音频单通道频域降噪，核心假设包括较高采样率、语音概率、OLA、FFT bin 独立估计等；当前传感器数据为多通道低频 ADC 帧序列。
- 自决方案：只参考其 Analyze/Process 双阶段、噪声估计、SNR/概率、处理器分离等架构思想；不直接采用音频分频器、OLA、语音概率模型和固定 256 点 FFT 流程。
- 自决理由：传感器数据没有语音频谱结构，且需求明确通道间不使用物理连接关系，逐通道统计框架更贴合数据形态。
- 风险预警：如果后续用户要求处理粉色/棕色噪声，可能需要补充频域/PSD 分析模块，但应作为 Analyzer 子模块而非音频 NS 照搬。
- 置信度：95%


#### Q8. 采样率如何处理？
- 问题描述：需求指出不同传感器采样率完全不一样；CSV 中部分文件头为 `录制频率,raw`，需要从时间戳差分估计实际采样率。
- 自决方案：Analyzer 优先读取文件头频率；若为 `raw` 或缺失，则从相邻时间戳差分估计 median Hz，并将采样率用于时间窗口长度换算，而不是用于固定帧数参数。
- 自决理由：这能让同一算法在 2Hz、10Hz、20Hz 等数据上保持相似的时间尺度。
- 风险预警：CSV 时间戳只有当天时间且无日期递增信息，跨午夜录制需另行处理；当前数据看起来不跨午夜。
- 置信度：93%

## v2 追加（开发中追加的问题，2026-07-10）

### 自决区

#### Q9. 动画窗口卡死 — `FuncAnimation(blit=False)` 全量重绘

- 问题描述：`replay_animator.py` 使用 `FuncAnimation(blit=False)`，每帧触发 Tk canvas 全量重绘。对于 4096 通道膜片数据，`canvas.draw()` 耗时约 46ms，在 10FPS (100ms interval) 下导致 timer backlog 累积，窗口失去响应。
- 自决方案：废弃 `FuncAnimation`，改用 `canvas.new_timer()` 手动控制循环；`_render_frame()` 中使用 `restore_region` + `draw_artist` + `blit` 手动 blit，仅每 10 帧调用一次 `draw_idle()` 更新文字。
- 自决理由：手动 blit 控制避免了全量重绘开销，且不依赖 `FuncAnimation` 的 timer 时序（后者在窗口未 mapped 时触发会崩溃）。
- 风险预警：TkAgg 的 `blit()` 通过 PhotoImage 拷贝，在真实窗口下单帧约 22-25ms，仍有优化的空间（如缩小 figure 尺寸）。
- 置信度：95%

#### Q10. `FuncAnimation(blit=True)` 在窗口未 mapped 前崩溃

- 问题描述：`FuncAnimation` 在 `__init__` 中创建时即注册 Tk timer，而 `plt.show()` 在之后才调用。timer 触发时 canvas 仍为 `FigureCanvasBase`，调用 `restore_region` 报 `AttributeError`。
- 自决方案：改为 `canvas.new_timer()`，仅在 `show()` 中先 `_render_frame()` 绘制第一帧真实数据，再启动 timer。此时窗口已 mapped，canvas 为 `FigureCanvasTkAgg`。
- 自决理由：`_build_figure()` 中先 `canvas.draw()` 初始化背景，`show()` 中先渲染再启动 timer，保证 canvas 处于就绪状态。
- 置信度：98%

#### Q11. `paused=True` 导致启动无动画（用户误认为卡死）

- 问题描述：`ReplayAnimator` 默认 `paused=True`，启动后 timer 虽触发 `_step()` 但不推进 `idx`，画面一直显示初始全零 heatmap。用户以为窗口卡死。
- 自决方案：改为 `paused=False`，启动即自动播放。
- 自决理由：用户期望的"启动动画窗口"意味着自动播放；按 Space 可随时暂停。
- 置信度：100%

#### Q12. `process` 与 `process_batch` threshold 计算不统一

- 问题描述：`noise_suppressor.py` 中 `process`（单帧）和 `process_batch`（批量）的处理逻辑等价但实现方式不一致（一个用 mask 清零，一个用 np.where），增加了阅读负担和出错风险。
- 自决方案：提取私有方法 `_apply()`，两者统一调用。
- 自决理由：消除代码重复，保持实现一致。
- 置信度：100%

#### Q13. 验收测试未覆盖 4096ch 膜片和动画循环

- 问题描述：`acceptance_replay_animator.py` 仅用 96ch 手套数据测试单帧渲染（Agg 后端，不启动 `plt.show()`），未覆盖 4096ch 膜片数据和实际动画循环。
- 自决方案：扩展验收测试覆盖三套设备，新增 `test_animation_perf.py`（模拟 120 帧 blit 循环）和 `test_real_render.py`（真实窗口压测）。
- 自决理由：验收测试必须覆盖所有设备类型和真实渲染路径。
- 置信度：95%

#### Q14. `tools` 包在 Python 3.14 下被 site-packages 遮蔽

- 问题描述：Python 3.14 的 site-packages 存在 `tools` 包，导致 `from tools.replay_animator import ReplayAnimator` 解析到错误路径。
- 自决方案：在 `tools/` 下新建空的 `__init__.py`，确保包被正确识别。
- 自决理由：这是标准的 Python 包修复方式，保证在任意 Python 版本下均可正确导入。
- 置信度：100%
